## Plan: Productize Local Azurite

Productize non-containerized Azurite by extending the existing Azure Storage emulator flow so `AddAzureStorage(...).RunAsEmulator(...)` can run either container-backed Azurite or a privately acquired local Azurite executable. The recommended first implementation path is a private acquisition flow that does not require machine-wide Azurite installation, stores emulator data under the AppHost/project folder by default, and preserves the existing Azure Storage connection-string, health-check, and child-resource behavior. Treat NuGet-backed acquisition as an evaluated alternative, but not the default unless Aspire owns a current first-party Azurite package or artifact; the public NuGet package currently visible is an old community package (`Azurite` 2.6.5, last updated 2018), which is not a solid productization base for current Azurite V3 behavior.

**Steps**
1. Phase 1: Lock the public API shape around the existing Azure Storage API. Keep the main entry point on `AddAzureStorage(...).RunAsEmulator(...)` rather than introducing a separate top-level Azurite API. Add options or overloads that distinguish container-backed versus local/private acquisition, while preserving today’s default container behavior for compatibility. Scope this phase to local Azurite only; do not broaden into LocalDB/SQL non-container flows in the same change.
2. Phase 1: Decouple emulator identity from container identity in the Azure Storage model. Refactor `AzureStorageResource.IsEmulator` and any related branching so emulator connection strings, endpoint URIs, Azure Functions config, blob/queue seeding, and readiness logic work for both container and executable launches. This is the key architectural prerequisite because current emulator behavior is gated on `IsContainer()`.
3. Phase 1: Introduce a local-emulator acquisition abstraction for Azurite. Model the launcher as executable-backed, not container-backed, but keep the same Azure Storage parent resource as the source of truth. The acquisition abstraction should support at least these strategies: a recommended private runtime install into an Aspire-managed cache/work folder, and a future first-party packaged-artifact strategy if the team later wants to avoid Node/npm completely.
4. Phase 2: Implement the recommended acquisition path as a private install, not a machine-wide prerequisite. The local launcher should resolve a private Azurite location under an Aspire-managed cache directory, install or hydrate Azurite there if missing, and then run it from that private location. Avoid relying on a globally installed `azurite` command. Use the existing private-cache patterns in the repo as guidance for stable cache placement rather than ephemeral temp-only extraction.
5. Phase 2: Evaluate acquisition backends explicitly and choose one in the implementation spec. Preferred near-term backend: private npm acquisition if Node/npm are available, with required-command validation and clear failure/help text. Secondary backend for later or separate work: Aspire-owned packaged artifact, potentially NuGet-backed, if the team wants to eliminate the Node/npm dependency. Do not plan around the current public `Azurite` NuGet package as-is because it is stale/community-owned and likely mismatched with current V3 behavior.
6. Phase 2: Define cache and data-path semantics separately. Tool binaries/package contents should live in a stable Aspire-managed cache outside the project tree so they are reused across runs and not redownloaded unnecessarily. Azurite data should live in the AppHost/project folder by default, matching the existing `WithDataBindMount()` semantics such as `.azurite/{resourceName}`, so persisted blob/queue/table data stays local to the app and does not require machine-wide installation.
7. Phase 2: Preserve today’s emulator runtime behavior for the local launcher. The executable path should emit the same effective arguments and endpoint semantics as the container flow: location/workspace path, blob/queue/table ports, `--disableProductStyleUrl`, and the current API-version-check behavior. Keep health checks side-effect-free and continue seeding blob containers and queues only after the emulator is healthy.
8. Phase 3: Rework the surrogate/emulator customization surface. Today `AzureStorageEmulatorResource` is container-specific because it inherits `ContainerResource` only to expose container methods over the same annotation set. Replace or generalize that pattern so local emulator configuration supports persistence path, ports, and emulator options without forcing container-only APIs such as volumes. Maintain backward compatibility for existing container customizations.
9. Phase 3: Update downstream composition points that implicitly assume Azurite means containerized Azure Storage. The most important one is Event Hubs emulator composition, which currently creates a sibling storage resource and calls `RunAsEmulator(...)` with container-lifetime propagation. Decide whether Event Hubs remains container-backed only for now, inherits the new local Azurite mode automatically, or gets a separate follow-up.
10. Phase 3: Add targeted tests covering the new branch without changing unrelated emulator families. Verify emulator detection, connection-string generation, Azure Functions configuration, executable arguments, default data directory selection, port overrides, seeding behavior, and persistence behavior. Add downstream tests for Event Hubs composition only for the chosen supported mode.
11. Phase 4: Add documentation and product guidance. Document that local Azurite is intended as a non-container on-ramp for development only, explain where the private tool cache lives versus where project data lives, and call out any remaining prerequisites such as Node/npm if the first implementation uses private npm acquisition.

**Decisions**
- Chosen direction: optimize first for a private, non-machine-wide acquisition flow.
- Chosen API direction: extend the existing Azure Storage API rather than creating a separate explicit top-level API.
- Included scope: productizing local Azurite as a first-class Azure Storage emulator option with project-local data persistence.
- Excluded scope: SQL/LocalDB productization, generalized non-container support for all emulators, and full redesign of unrelated emulator resources.
- Acquisition recommendation: do not depend on globally installed Azurite. Prefer a private acquisition/cache flow. Treat a first-party packaged artifact as a valid future refinement if avoiding Node/npm becomes a product requirement.
- NuGet note: a public NuGet package named `Azurite` exists, but the currently visible package is old and community-owned (`2.6.5`, 2018). It should not be treated as the productized acquisition answer unless the team validates it or replaces it with a maintained first-party artifact.

**Further Considerations**
1. Event Hubs compatibility recommendation: keep Event Hubs emulator on its current container path initially unless there is a strong requirement to inherit local Azurite immediately. That keeps the first productization slice small and avoids mixing two emulator-mode changes in one PR.
2. Cache-location recommendation: use a stable Aspire-managed cache for acquired Azurite bits and reserve the project folder for user data only. Running directly from a temp-only extraction location would satisfy the letter of the ask but creates unnecessary churn, slower restarts, and harder offline reuse.
3. Artifact strategy recommendation: if the team wants a no-Node story long term, plan a second phase that produces or consumes an Aspire-owned packaged Azurite artifact rather than depending on the stale public NuGet package.
